# 项目现状与实施计划

## 1. 审计结论

当前仓库是一个可运行的本地原型，不是可直接部署到 Cloudflare Pages 的生产应用。项目没有被重建，本次检查也没有修改现有业务功能。

## 阶段 1 完成情况

阶段 1“用户资料和双赛道系统”已经完成：

- 用户资料增加姓名、学号、校区、所属赛道、账号状态和创建时间。
- 建立“四校区互动赛道”和“自律健康赛道”。
- 管理员可查看、添加、编辑、禁用/启用用户，并导入 `.xlsx` 名单。
- 普通用户只能通过 `/api/me` 查看自己的只读身份资料。
- 禁用账号不能重新登录，已有令牌也会失效。
- 旧 JSON 数据通过可重复执行的迁移补齐新字段，迁移前自动备份。
- 已增加登录、编辑、Excel 导入、禁用和越权访问自动测试。

## 阶段 2 完成情况

阶段 2“四校区互动赛道队伍系统”已经完成：

- 最大队伍数量持久化在 `config.maxTeams`，默认迁移值为 50。
- 管理员可增加或减少名额，但不得低于当前已有队伍数量。
- 管理员可创建队伍、修改名称和人数限制、查看及移除成员。
- 空队伍可解散；有成员的队伍必须先移除成员，服务端拒绝直接删除。
- 四校区互动赛道学生可查看队伍列表、查看我的队伍并通过邀请码加入。
- 自律健康赛道不能加入或查看互动赛道队伍。
- 服务端强制一个学生只能加入一个队伍，并在满员时拒绝加入。
- 阶段 2 数据迁移会在首次执行前备份 `db.json`。

## 阶段 3、4 完成情况

- 管理员可创建和编辑双赛道任务，支持草稿、发布、关闭、归档，以及时间、补交、图片上限和文案要求。
- 活动总开关和两个赛道开关已持久化；任务状态及所有提交时间由服务端验证。
- 互动赛道按队伍提交且每队每任务唯一；健康赛道按个人和早餐/午餐/晚餐提交。
- 支持草稿、最终提交、公开选择、退回和通过；最终提交后禁止重复覆盖。
- `version` 乐观锁与服务端写入队列阻止队友同时保存时静默覆盖。
- 上传前在浏览器压缩，服务端验证格式、文件签名和大小；数据库只保存图片 URL。
- 本地预览沿用 `uploads/` 对象目录；Cloudflare 正式部署仍需提供 R2 绑定。

## 阶段 5 完成情况

- 四校区队伍最终提交且选择公开时，由服务端自动生成广场帖子；不存在自由发帖接口。
- 帖子保存任务、队伍和成员快照、图片 URL、文案、发布时间、浏览量、点赞用户及可见状态。
- 支持最新发布、热门排行、上海时区月度排行、分页加载和原生图片懒加载。
- 登录用户可浏览和切换点赞；打开详情时服务端累计浏览量。
- 管理员可隐藏、恢复和永久删除帖子，删除不影响原任务提交记录。
- 本阶段没有评论、私信和自由发帖。

## 阶段 7 完成情况

- 日榜和周榜分别生成点赞榜、浏览榜、综合热度榜。
- 综合热度使用最大值归一化：`点赞归一化 × 70 + 浏览归一化 × 30`，不直接相加，不使用 AI。
- 月榜按队伍统计公开次数、周期内有效点赞、周期内有效浏览和综合热度。
- 被管理员排除排名的帖子不会进入任何实时排行榜。
- 管理员可冻结指定月份的最终快照，冻结后读取和导出均使用不可变快照。
- 管理员可导出中文 `.xlsx` 排行榜。

## 阶段 8 完成情况

- 后台数据看板展示用户、队伍、今日提交、可见公开帖子、当前有效点赞和去重浏览数量。
- 任务提交支持查看图片和文案、通过、退回和永久删除；删除会同步清理关联广场帖子及互动统计。
- 广场管理支持隐藏、恢复、删除、排除排名和恢复排名。
- 管理员可导出用户名单、队伍名单、打卡记录、指定日期缺卡名单、指定月份排行榜和材料清单。
- 导出文件为中文 `.xlsx`，学号列强制文本格式，避免科学计数法。
- 所有看板、审核、管理和导出接口均要求管理员权限。

## 阶段 9 完成情况

- 管理员可创建标题、描述、截止时间、允许扩展名、文件上限、总结要求和个人/队伍模式的材料任务。
- 学生查看适用任务、上传文件、填写总结并查看已提交或退回修改状态。
- 队伍任务沿用四校区队伍关系，每队每任务只有一条材料记录，并使用版本号阻止覆盖。
- 管理员可查看文件与总结、鉴权下载并填写原因退回修改。
- 管理员可导出个人或队伍模式的未提交名单，学号保持文本格式。
- 文件保存在非静态 `material-files/`；只有提交本人、所属队伍成员或管理员可通过鉴权 API 下载。
- 初次提交执行截止时间校验；管理员退回后允许补充修改。

## 任务日程与统一编队调整

- 管理员可选择按活动第几天（例如第 1、3、5 天）、指定星期或单次方式生成任务。
- 活动日模式在开始/结束日期内按日序生成 `occurrenceDate`，学生端跨日自动刷新任务栏。
- 每期只能提交服务器上海日期当天材料，并执行管理员设置的每日开始/结束时间；最多 3 张且不允许补交。
- 四校区公开勾选改为“同意发布至活动广场”，勾选后必须填写独立作品文案，广场使用该文案。
- 学生自助邀请码加入默认关闭；管理员可按学号加入、踢出成员。
- 队伍 Excel 支持“队伍名称+每行一个学号”或“队伍名称+成员1～成员4学号”，导入时自动校验赛道、满员和一人一队。

## 阶段 6 完成情况

- 点赞从帖子内数组升级为独立 `plazaLikes[]` 记录，服务端按上海自然日限制每人最多 5 个有效点赞。
- 点赞和取消改为幂等目标状态；重复请求不会反复切换，取消后立即恢复当天额度。
- 浏览使用 `plazaViews[]` 保存用户、帖子和 24 小时窗口；只有进入详情调用浏览接口才统计。
- 同一用户同一帖子 24 小时内只计一次，管理员访问不计数。
- 写入队列和保存前组合唯一性检查共同阻止多窗口突破额度、刷赞和重复记录。

### 已确认的结构

1. `public/index.html` 只提供挂载节点并加载 `style.css`、`app.js`。
2. `public/app.js` 通过字符串模板渲染宣传页、登录、学生打卡页和管理员后台。
3. `server.js` 同时提供静态文件、认证、打卡和管理员 API。
4. `data/db.json` 保存配置、用户和打卡记录。
5. `uploads/` 保存 Base64 解码后的图片文件。
6. `启动打卡网站.cmd` 在 Windows 上启动 Node 服务并打开 Edge。

## 2. 当前业务行为

- 账号由管理员创建，学生使用学号和密码登录。
- 服务端使用 Asia/Shanghai 时区判断当天日期和时间。
- 学生只能提交当天材料，并且只能在配置的早餐、午餐、晚餐窗口提交。
- 同一学生、日期和时段再次提交时，记录会被替换。
- 管理员可查看指定日期全部学生的提交状态，查看图片并通过或驳回。
- 管理员可修改活动名称和三个时段，可创建学生账号。

## 3. 当前主要问题

### P0：上线阻塞

- 密码仍以明文存储；阶段 1 已停止在 API 响应中返回密码字段。
- 登录令牌只是可伪造的 Base64 用户 ID，没有签名、过期时间或服务端会话。
- 内置管理员账号和默认密码已存在于公开仓库。
- 上传图片通过 `/uploads/...` 无鉴权公开访问。
- 没有 HTTPS、登录限流、密码修改/重置、会话吊销或审计日志。
- 本地 JSON 和文件系统不适用于 Cloudflare Pages，也无法保证多人并发写入安全。

### P1：数据可靠性和规则一致性

- `data/db.json` 是整文件读写；并发请求可能相互覆盖或造成文件损坏。
- 重新提交会删除旧记录，但不会删除旧图片，长期运行会产生孤立文件。
- `startDate`、`endDate` 只保存不执行，活动日期外仍可按时段打卡。
- 管理员配置没有严格字段校验，可提交不完整或异常结构。
- 宣传页的时段与“18天”等文案写死，管理员修改配置后不会同步。
- 管理员已可编辑、重置密码和禁用账号；仍没有删除账号功能。
- 被驳回记录在学生页面仍显示为“待审核”，状态表达不完整。

### P2：工程和可维护性

- 已增加 `package.json` 和 Node.js 自动测试；仍没有 TypeScript、ESLint、格式化、构建或 CI。
- 前后端代码高度压缩在少数长行中，审查和维护困难。
- `adminFor` 临时覆盖全局 `Date.prototype.toLocaleDateString`，异常时可能无法恢复。
- 前端采用 `innerHTML`；转义函数不覆盖引号，配置值进入属性时存在注入风险。
- 没有结构化日志、备份、数据导出、保留周期或故障恢复方案。

## 5. 建议的后续实现方式

建议保留现有页面视觉和业务流程，分阶段迁移，不重建全部界面。

### 阶段 A：安全基线

1. 定义正式用户模型，密码使用强哈希；API 永不返回密码字段。
2. 使用签名、短时会话和 HttpOnly/Secure Cookie，增加退出和会话撤销。
3. 增加登录限流、权限中间件、输入校验和安全响应头。
4. 将上传图片改为受保护对象，管理员或所属学生经鉴权后访问。
5. 增加管理员首次初始化和强制修改密码流程。

### 阶段 B：Cloudflare 数据层

1. 将 API 迁移到 Cloudflare Workers 或 Pages Functions。
2. 使用 D1 保存用户、配置、打卡和审核记录。
3. 使用 R2 保存原图，D1 只保存对象键、元数据和状态。
4. 使用 Wrangler migrations 管理数据库结构。
5. 使用 Cloudflare Secrets 保存会话密钥，不写入仓库。

### 阶段 C：工程化和部署

1. 新增最小 `package.json`，定义 `dev`、`lint`、`typecheck`、`test`、`build`。
2. 在不改变页面功能的前提下逐步拆分前端和 API 模块。
3. 增加 API 单元测试、权限测试、时段边界测试和上传测试。
4. 配置 GitHub Actions 在 PR/推送时运行检查。
5. Cloudflare 先部署预览环境，验收后再绑定生产域名。

## 6. 上线验收门槛

- 不存在明文密码或可伪造令牌。
- 学生不能访问他人材料；未登录用户不能访问任何上传图片。
- 时段边界、活动日期、重复提交和审核状态均有自动测试。
- D1/R2 有备份和数据保留策略。
- GitHub CI 全部通过，Cloudflare 预览环境完成移动端和管理员验收。
